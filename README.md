## 1.2. Пояснення (інтерпретація) отриманих на графіку результатів
На згенерованому `flamegraph_O0.svg` вісь Y відображає глибину стека викликів функцій, а вісь X показує не хронологічний час, а відносну частку семплів (відсоток процесорного часу), зайняту відповідними викликами.

Аналізуючи отриманий графік для програми множення матриць без оптимізації (`-O0`), можна зробити такі висновки:
- **Домінування обчислювального явища (O(N^3)):**
   Весь простір графіка заповнений блоками програми `matrix_О0`, що свідчить про те, що центральний процесор задіяний переважно на виконанні математичних операцій всередині вкладених циклів наївного алгоритму.
 - **Вплив системного середовища та бібліотек:**
   У нижній частині графіка присутні базові виклики ініціалізації (`libc.so.6` та початкові шари виконання програми), проте їхня частка мінімальна порівняно з основною обчислювальною роботою.
- **Наслідки відсутності оптимізації:**
   Оскільки компіляція виконувалася з прапорцем `-O0`, компілятор не здійснював векторизацію, розгортання циклів чи кешування проміжних даних у регістрах. Це призвело до створення глибоких стекових структур та великої кількості зайвих операцій із пам'яттю, що чітко візуалізується у вигляді вертикальних «веж» і широких плато на графіку.

# 2. Збір та аналіз статистики виконання програми

Для глибокого аналізу продуктивності програми множення матриць без оптимізації (`-O0`) було використано три стандартні системні утиліти.

## 2.1. `/usr/bin/time --verbose ./matrix_О0`

Команда дозволяє отримати детальні системні метрики часу виконання, використання пам'яті та накладних витрат процесора:
* **User time:** ~22.28 с — час виконання безпосередньо коду програми (алгоритму множення)
* **System time:** ~0.01 с — накладні витрати ядра ОС мінімальні, оскільки програма є інтенсивною обчислювальною задачею (CPU-bound).
* **Percent of CPU this job got:** завантаження процесора становить 99%. Це вказує на те, що ядро інтенсивно виконує математичні цикли наївного алгоритму.
* **Elapsed (wall clock) time:** ~0:22.31 — реальний час виконання програми від запуску до завершення. Майже повна відповідність до User time (22.28 с) підтверджує відсутність зовнішніх затримок чи блокувань під час роботи.
* **Maximum resident set size:** ~16444 КБ — пікове споживання RAM (близько 16 МБ), що повністю відповідає розміру трьох масивів 1024x1024 типу `float`.
* **Major page faults:** 4 — «жорсткі» промахи сторінок із зверненням до диска (I/O). Їхня мінімальна кількість свідчить про те, що накладні витрати на завантаження програми з носія були практично непомітними.
* **Minor page faults:** ~3228 — «м'які» промахи сторінок, які виникають при першому зверненні до віртуальної пам'яті, коли ОС фізично виділяє сторінки в оперативній пам'яті під матриці.
* **Context switches:** добровільних (Voluntary): 8, примусових (Involuntary): 117. Невелика кількість перемикань підтверджує стабільне виконання процесу без зайвих переривань з боку планувальника ОС.

## 2.2. `perf stat -d ./matrix_O0`

* **Instructions per cycle (IPC): ~0.99 (або до 2.58 залежно від прогону)** — показник ефективності використання процесорного ядра, що демонструє кількість виконаних інструкцій за один такт.
* **Cycles / Instructions:** ~59.3 млрд тактів та ~58.9 млрд інструкцій.
 * *Пояснення:*  через специфіку наївного алгоритму процесор значну частину часу очікує на дані.
* **L1-dcache-load-misses: ~1.09 млрд промахів кешу L1.** 
  * *Пояснення:* Такий високий показник промахів зумовлений колізією між порядком зберігання даних у пам'яті C++ (row-major, рядок за рядком) та логікою наївного алгоритму. Оскільки доступ до матриці B відбувається по стовпцях, порушується принцип просторової локальності. Процесор завантажує в кеш цілу лінію обсягом 64 байти, але застосовує з неї лише 4 байти (одне значення float), після чого інформація втрачає актуальність. Це спричиняє мільярди циклів очікування (stalls) на шині пам'яті при зверненні до оперативної пам'яті.
* **Branch-misses: ~0.01%** — надзвичайно низький відсоток хибних передбачень умовних переходів завдяки регулярній структурі циклів.
* **CPUs utilized: ~0.999** — програма повністю використовує одне ядро центрального процесора (99.9%).


## 2.3. `perf report` (after `perf record) `
   ```bash
   sudo perf record -g -- ./matrix_O0
   sudo perf report
   ```
У звіті `perf report` із увімкненим деревом викликів (`-g`) чітко видно, що 99.99% процесорного часу припадає на виконання нашої програми (`matrix_O0`). Відсотки на гілках дерева демонструють розподіл «гарячих точок» (hotspots) всередині вкладених циклів множення матриць. Це підтверджує, що вузьким місцем є не накладні витрати ОС, а чисті обчислення та робота з пам'яттю в тілі алгоритму.

# 3. Вимірювання енерговитрат (Power consumption)
Через архітектурні обмеження середовища віртуалізації WSL2 (відсутність прямого доступу до низькорівневих датчиків RAPL на рівні ядра Linux), вимірювання енергоспоживання проводилось на хост-системі Windows за допомогою утиліти HWiNFO64. З логів моніторингу датчика `CPU Package Power` (з інтервалом логування 2 секунди) було отримано реальні показники потужності (див. графік `matrix_mult_graph.png`):
* **Час виконання програми (T):** 20.77 с
* **Фонове споживання(P_{idle}):** ~ 6.95 Вт
* **Споживання під навантаженням(P_{load}):** ~ 16.11 Вт

## 3.1. Енерговитрати системи при виконанні програми
Загальна енергія, спожита системою під час виконання розрахунків:
$$E_{sys} = P_{load} \times T = 16.11 \text{ Вт} \times 20.77 \text{ с} \approx 334.60 \text{ Дж}$$

## 3.2. Енерговитрати виключно досліджуваної програми
Для визначення чистого енергоспоживання алгоритму було вираховано різницю потужностей ($\Delta P$):
$$\Delta P = P_{load} - P_{idle} = 16.11 \text{ Вт} - 6.95 \text{ Вт} = 9.16 \text{ Вт}$$
Енергія, витрачена безпосередньо на виконання програми:
$$E_{prog} = \Delta P \times T = 9.16 \text{ Вт} \times 20.77 \text{ с} \approx 190.25 \text{ Дж}$$
